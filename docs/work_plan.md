## 1. המשימה בקצרה

אפליקציה קטנה שמחזירה את כתובת ה-IP הציבורית של הלקוח, עם פייפליין CI/CD מלא שפורס אותה ל-Kubernetes עם Helm.

**מה צריך להגיש:**

- ריפו ב-GitHub עם קוד, טסטים וקובץ README ברור
- אפליקציה עם שלוש נקודות קצה: `/`, `/health` ו-`/ready`
- קובץ Dockerfile רב-שלבי עם אימג' מינימלי, וקובץ `.dockerignore`
- צ'ארט Helm בתיקייה `charts/`, עם Deployment ו-Service. Ingress הוא אופציונלי.
- בקובץ `values.yaml` אפשר להגדיר את ה-probes ואת המשאבים
- פייפליין שרץ על push ועל PR, בסדר הזה:
  lint → tests → build → scan → push → helm lint → deploy → smoke test
- התראה על הצלחה או כישלון
- רכיב AI שרץ רק בכישלון: אוסף את הלוגים, שולח למודל שפה ומפרסם אבחון
- תיעוד: איך מריצים מקומית, איך ה-CI עובד, איפה האימג' מתפרסם ואיך מספקים סודות
- קישור לריצה שנכשלה, שבה רכיב ה-AI עבד

## 3. מוסכמות

### קומיטים

- מתחילים באות גדולה ובפועל בציווי
- בלי קידומות כמו `feat:` או `fix:`
- שורת כותרת קצרה, עד בערך 50 תווים, בלי נקודה בסוף
- קומיטים קטנים, ושינוי לוגי אחד בכל קומיט

דוגמאות:

```
Add health and readiness endpoints
Add multi-stage Dockerfile with non-root user
Configure Trivy scan to fail on critical findings
```

### אבטחת הפייפליין

- **כל GitHub Action חיצוני נעוץ ל-commit SHA מלא**, ולא לתגית כמו `@v4`.
  - הסיבה: במרץ 2026 תוקפים דחפו בכוח קוד זדוני ל-76 מתוך 77 התגיות של `aquasecurity/trivy-action`. כל workflow שהשתמש בתגית הריץ קוד שגונב סודות. SHA הוא בלתי ניתן לשינוי.
  - ליד כל SHA כותבים בהערה את הגרסה, כדי שיהיה קריא.
- **הרשאות מינימליות ל-`GITHUB_TOKEN`**, ומגדירים אותן בכל ג'וב בנפרד.

### תיעוד שוטף

- **יומן החלטות** בתיקייה `docs/decisions/`, בפורמט ADR קצר: הקשר, האפשרויות שנבחנו, ההחלטה והסיבה.
- **יומן תקלות** בקובץ `docs/troubleshooting.md`: התסמין, הסיבה והפתרון לכל בעיה שניתקל בה.
  - רשומה ראשונה: ב-WSL2, שירות עם `sessionAffinity: ClientIP` לא נגיש, וגם שום שירות שנוצר אחריו, כי חסר מודול בקרנל ש-kube-proxy צריך. ההגדרה הזו לא קשורה לזיהוי כתובת הלקוח, ולא משתמשים בה.

## 4. החלטות שהתקבלו ✅

### החלטה 1: שפה וספרייה – Python עם FastAPI
- **למה:** רעות מכירה את Python. המשימה נותנת את flake8 כדוגמה ללינטר, וזה רמז לשפה, לא לספרייה. FastAPI מודרנית, ויש לה כלי טסטים מובנה.
- **חלופות שנבחנו:** Flask; Go, שהאימג' שלה הכי קטן אבל היא פחות מוכרת לרעות; Java עם Spring Boot, שהאימג' שלה כבד.
- **מחיר ההחלטה:** אימג' של Python גדול יותר. מצמצמים את זה עם בנייה רב-שלבית ואימג' בסיס רזה.

### החלטה 2: ארכיטקטורת CI – היברידית
- **על הרנרים של GitHub:** lint, טסטים, build, scan ו-push.
- **על רנר מקומי שפורס ל-Kubernetes אצל רעות:** helm lint, deploy ל-staging ו-smoke test.
- **למה:** רנר מקומי בריפו ציבורי הוא סיכון אבטחה, כי PR מפורק יכול להריץ קוד על המחשב. לכן רק מה שחייב את הקלאסטר רץ מקומית.

### החלטה 3: הצמצום של סיכוני הרנר המקומי

### החלטה 5: רכיב ה-AI – ג'וב אחרון בפייפליין
- **הפעלה:** רץ רק כשאחד הג'ובים הקודמים נכשל, עם התנאי `if: failure()`.
- **למה לא workflow נפרד:** הריפו פרטי, ולכן היתרון של הגנה מפורקים כמעט לא רלוונטי. ג'וב באותו פייפליין מתאים מילה במילה לניסוח של המשימה, CI step that runs only when the pipeline fails. רואים אותו באותו גרף של הריצה, וקל לבדוק אותו.
- **התכנון:**
  - סקריפט Python קטן, עם טסטים משלו
  - אוסף רק את הלוגים של הג'וב שנכשל, חותך אותם לקטע הרלוונטי ומסנן סודות
  - מבקש מהמודל תשובה במבנה קבוע: שורש הבעיה, השלב שנכשל, הצעת תיקון ורמת ביטחון
  - מפרסם תגובה אחת מעוצבת על ה-PR, עם קישור לריצה, ומעדכן אותה במקום להוסיף חדשות
  - אם המודל לא זמין, מפרסם הודעת כישלון רגילה
  - הלוגים נחשבים קלט לא אמין: לא מריצים שום דבר שמגיע מהם, רק מפרסמים טקסט
  - ענף הדגמה שנכשל בכוונה, כדי שיהיה קישור לריצה שנכשלה

### החלטה 13: סריקת אבטחה – Trivy דרך ה-Action נעוץ ל-SHA
- **הכלי:** Trivy, הכלי הנפוץ ביותר לסריקת קונטיינרים ב-GitHub Actions, בקוד פתוח. החלופה המרכזית שנבחנה: Grype יחד עם Syft.
- **איך מריצים:** ה-Action הרשמי `aquasecurity/trivy-action`, נעוץ ל-commit SHA מלא, עם הגרסה בהערה. לפני שבוחרים SHA, מוודאים שהגרסה בטוחה ושהיא לא אחת מאלה שנפגעו במרץ 2026.
  - **חלופה שנבחנה:** להתקין את הבינארי בגרסה קבועה, עם בדיקת checksum. נדחתה כי היא דורשת יותר שורות לתחזק, ואין בה קאש מובנה.
- **איפה:** אחרי הבנייה, לפני ה-push ל-GHCR. אימג' פגיע לא מגיע לרג'יסטרי.
- **מתי נכשלים:** על ממצאים ברמת CRITICAL ו-HIGH, עם `ignore-unfixed`, כדי לא להיכשל על חולשות שעוד אין להן תיקון. חריגות מוצדקות נרשמות בקובץ `.trivyignore`, עם הסבר.
- **SBOM:** בפורמט CycloneDX, נשמר כ-artifact של הריצה.
- **הדוח:**
  - תמיד: טבלה בסיכום הריצה, ודוח SARIF שנשמר כ-artifact.
  - ללשונית Security: ההעלאה רצה רק כשהריפו ציבורי, עם התנאי `if: ${{ !github.event.repository.private }}`. בריפו פרטי של חשבון אישי, סריקת קוד דורשת GitHub Code Security, וההעלאה הייתה נכשלת.
  - הרשאה נדרשת להעלאה: `security-events: write`.

### החלטה 14: lint ופורמט – ruff לקוד Python, ו-hadolint ל-Dockerfile
- **למה ruff ולא flake8:** flake8 רק מדווח על בעיות. לידו צריך גם black לפורמט וגם isort לסידור ה-imports, כלומר שלושה כלים ושלוש גרסאות לנעוץ. ruff עושה את שלושתם, עם אותם קודים של חוקים כמו flake8, וכולל מובנים חוקים שב-flake8 דורשים תוספים, כמו bugbear וחוקי אבטחה בסגנון bandit. הוא יודע לתקן אוטומטית, וכל ההגדרות שלו יושבות ב-`pyproject.toml`.
- **מחיר ההחלטה:** ruff פרויקט צעיר יותר, ויש מאחוריו חברה מסחרית. המשימה נותנת את flake8 רק כדוגמה.
- **hadolint:** הכלי המקובל ללינט של Dockerfile. רץ דרך `hadolint/hadolint-action`, נעוץ ל-SHA מלא.
- **בפייפליין:** `ruff check`, `ruff format --check` ו-`hadolint`.

### החלטה 15: זיהוי ה-IP של הלקוח – uvicorn עם NetworkPolicy
- **האיום:** כל לקוח יכול לשלוח בעצמו כותרת `X-Forwarded-For` עם כתובת מזויפת. במערכת אמיתית אותה כתובת משמשת להגבלת קצב, לרשימות של כתובות מורשות, ללוגים ולחסימה לפי מדינה.
- **שכבה 1, Traefik:** בלי `trustedIPs` ובלי `insecure`, כי אין שום פרוקסי לפניו. מאמתים בניסוי מה הוא עושה עם כותרת שמגיעה מבחוץ.
- **שכבה 2, האפליקציה:** המנגנון המובנה של uvicorn, `--proxy-headers`, שקורא את הכותרת מימין ומדלג רק על כתובות מהימנות. את הרשימה מגדירים במשתנה `FORWARDED_ALLOW_IPS`, שמוגדר בקובץ `values.yaml` לטווח הכתובות של הפודים. אף פעם לא מגדירים אותו ל-`*`. הקוד מחזיר רק את `request.client.host`, ולא מנתח כותרות בעצמו.
- **שכבה 3, NetworkPolicy:** מכיוון שסומכים על כל טווח הפודים, פוד פרוץ בקלאסטר יכול לזייף את הכותרת. לכן מוסיפים בצ'ארט NetworkPolicy, עם מתג, שמאפשר לפנות לאפליקציה רק מה-namespace של Traefik. מקורות סותרים לגבי תמיכה של kindnet ב-NetworkPolicy, ולכן מאמתים בניסוי שפוד אחר נחסם.
- **בדיקות:** טסט יחידה שבו כותרת מכתובת לא מהימנה נזרקת, טסט שבו כותרת מכתובת מהימנה מתקבלת, ובבדיקת העשן שולחים כותרת מזויפת דרך Traefik ומוודאים שהיא לא חוזרת.
- **חלופות שנבחנו:** לנתח את הכותרת בקוד שלנו, שזה יותר קוד ויותר מקום לבאגים. לסמוך על כל כתובת עם `*`, שזה בטוח רק אם הדלת נעולה.

### החלטה 16: ניהול תלויות – uv עם uv.lock
- **איך:** התלויות מוגדרות ב-`pyproject.toml`, ו-`uv.lock` נשמר בגיט, עם כל עץ התלויות, הגרסאות וה-checksums. תלויות הפיתוח, כמו pytest ו-ruff, נמצאות בקבוצה נפרדת ולא נכנסות לאימג'.
- **ב-Docker:** שלב הבנייה מריץ `uv sync --frozen --no-dev`, ולשלב הסופי מעתיקים רק את ה-venv. uv עצמו לא נכנס לאימג'. את האימג' של uv נועצים לגרסה.
- **ב-CI:** ה-Action `astral-sh/setup-uv`, נעוץ ל-SHA.
- **מחיר ההחלטה:** צריך להתקין uv מקומית. uv ו-ruff שייכים שניהם ל-Astral, כלומר תלות בספק אחד.
- **חלופות שנבחנו:** pip עם pip-tools, שהם שני כלים ושני קבצים. pip עם `requirements.txt` פשוט, שלא נועל תלויות של תלויות ולא שומר checksum.

## 5. בבדיקה אצל רעות 🔍

### ניתוב תעבורה: Ingress מול Gateway API
רעות חוקרת את הנושא ותחליט בהמשך. אפשר להתקדם בשאר העבודה בינתיים.

- **אפשרות א, רק Ingress:** הכי פשוט, ותואם מילה במילה למשימה, שכתוב בה optional Ingress.
- **אפשרות ב, רק Gateway API:** הכי מודרני. פרויקט Kubernetes ממליץ על Gateway, וה-API של Ingress הוקפא. הסיכון הוא שהבודק יחפש משאב Ingress.
- **אפשרות ג, שניהם בצ'ארט עם מתג:** `ingress.enabled` ו-`httpRoute.enabled`. ביום הראשון בונים Ingress, וביום השני מוסיפים HTTPRoute אם יש זמן.
- **ההמלצה של Claude:** אפשרות ג.
- **מה צריך לזכור ב-Gateway API:** את ה-CRDs שלו צריך להתקין, כי הם לא מובנים ב-Kubernetes.

### ה-controller: ההמלצה היא Traefik
- **למה לא ingress-nginx:** הפרויקט פרש במרץ 2026. אין יותר גרסאות, תיקוני באגים או תיקוני אבטחה.
- **למה לא cloud-provider-kind:** נבדק בעיקר על Linux. ב-Windows התמיכה בסיסית, הוא דורש הרשאות מנהל, ויש דיווחים על timeout ב-WSL2.
- **למה Traefik:**
  - רץ בתוך הקלאסטר ומותקן עם Helm, כך שבדיקת העשן יכולה לפנות אליו מבפנים
  - תומך גם ב-Ingress וגם ב-Gateway API, ולכן ההחלטה על Traefik לא תלויה בהחלטה הקודמת
  - מגרסה 2, לא סומך על כותרות X-Forwarded כברירת מחדל. מגדירים ממי לסמוך עם `trustedIPs`.
- **המחיר:** עוד פוד שרץ כל הזמן, ותלות בכלי שיש מאחוריו חברה מסחרית. הצ'ארט משתמש במשאבים סטנדרטיים, ולכן אפשר להחליף controller.
- **הגנה בשכבות:** Traefik לא מעביר כותרת מזויפת שהגיעה מבחוץ, והאפליקציה סומכת רק על כותרות שהגיעו מ-Traefik.

## 7. בדיקת משאבים במחשב 🖥️

**מטרה:** לדעת בוודאות כמה זיכרון, מעבד ודיסק נשארים כש-Docker Desktop, kind ו-ARC רצים. ככה מחליטים על סמך מספרים ולא הנחות. **זה הצעד הראשון לפני הקמת הקלאסטר.**

**רקע:** המחשב של רעות עם Windows, 4 ליבות ובערך 22 ג'יגה זיכרון זמין. ל-WSL מוגבלים 6 ג'יגה ו-4 מעבדים, בקובץ `.wslconfig`. Docker Desktop רץ בתוך WSL, ולכן הוא חולק את אותה מגבלה.

**ההחלטה על הרנר לא משתנה:** ממשיכים עם קונטיינר Docker זמני, כמו בהחלטה 10. המדידה של ARC רק בודקת אם יש מקום לעבור אליו בהמשך.

### שלב 1: מדידת בסיס, Docker Desktop פועל ושום דבר אחר לא רץ

ב-PowerShell:

```powershell
Get-PSDrive C                       # מקום פנוי בדיסק C
Get-Content $env:USERPROFILE\.wslconfig   # המגבלות שהוגדרו ל-WSL
wsl --list --verbose                # אילו הפצות WSL רצות
```

בתוך WSL:

```bash
free -h            # זיכרון: כמה מוקצה, כמה בשימוש, כמה זמין
nproc              # כמה מעבדים WSL רואה
df -h /            # מקום בדיסק בתוך WSL
docker system df   # כמה מקום תופסים אימג'ים, קונטיינרים ו-volumes
docker stats --no-stream
```

### שלב 2: אחרי הקמת kind

- להקים קלאסטר kind עם קובץ ההגדרות של הפרויקט
- להתקין metrics-server. ב-kind צריך להוסיף את הדגל `--kubelet-insecure-tls`, כי לקובלט אין תעודה חתומה.
- למדוד במנוחה:

```bash
free -h
docker stats --no-stream        # כמה צורך הקונטיינר של הנוד
kubectl top nodes
kubectl top pods -A
```

### שלב 3: אחרי התקנת Traefik
- אותן מדידות, כדי לראות כמה ה-controller מוסיף.

### שלב 4: אחרי התקנת ARC
- להתקין את הצ'ארט של הקונטרולר, `gha-runner-scale-set-controller`.
- כדי להרים גם את ה-listener צריך להתקין scale set שמחובר לריפו, וזה דורש טוקן או GitHub App. אם אין עדיין, מודדים רק את הקונטרולר, ומתעדים את זה.
- למדוד במנוחה, ואם אפשר גם בזמן ג'וב, כשנוצר פוד של רנר.

### שלב 5: סיכום
- לרשום את כל המדידות בקובץ `docs/resource-baseline.md`, בטבלה: מה רץ, זיכרון, מעבד ודיסק.
- **כלל החלטה מוצע:** אם אחרי kind, Traefik ו-ARC נשאר פחות מבערך ג'יגה וחצי זיכרון פנוי ב-WSL, נשארים עם קונטיינר Docker. הסיבה: הבנייה של האימג' והטסטים צריכים מקום.

## 8. מידע רקע מהמחקר

- **רנר מקומי בריפו ציבורי:** GitHub ממליצה לא לחבר רנר מקומי לריפו ציבורי. ההגנה המובנית דורשת אישור רק ל-PR הראשון של תורם חדש.
- **עלות רנר מקומי:** GitHub הודיעה בדצמבר 2025 על תשלום לפי דקה, ודחתה את זה. נכון לעכשיו השימוש חינמי.
- **צריכת זיכרון של kind:** נוד אחד צורך במנוחה בערך 300 עד 600 מגה. ב-WSL של רעות הוקצו 6 ג'יגה.
- **זיהוי ה-IP:** מאחורי פרוקסי או Ingress, הכתובת מגיעה בכותרת X-Forwarded-For. ב-Service, ההגדרה `externalTrafficPolicy: Local` שומרת על כתובת המקור.
- **מה רואים מקומית:** ב-kind לא רואים כתובת ציבורית, אלא כתובת של רשת Docker, משהו כמו `172.18.0.1`. זה צפוי, ונתעד את זה ב-README.
- **ניסוי מוצע:** נקודת קצה זמנית לדיבאג, שמחזירה את כתובת החיבור ואת כל הכותרות. מריצים דרך port-forward, דרך NodePort ודרך ה-Ingress, ומתעדים מה מגיע בכל אחת. אחר כך מוחקים אותה.
