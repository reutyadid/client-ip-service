## 1. המשימה בקצרה

אפליקציה קטנה שמחזירה את כתובת ה-IP הציבורית של הלקוח, עם פייפליין CI/CD מלא שפורס אותה ל-Kubernetes עם Helm.

**מה צריך להגיש:**

- ריפו ב-GitHub עם קוד, טסטים וקובץ README ברור
- אפליקציה עם שלוש נקודות קצה: `/`, `/health` ו-`/ready`
- קובץ Dockerfile רב-שלבי עם אימג' מינימלי, וקובץ `.dockerignore`
- צ'ארט Helm בתיקייה `charts/`, עם Deployment ו-Service. Ingress הוא אופציונלי.
- בקובץ `values.yaml` אפשר להגדיר את ה-probes ואת המשאבים
- פייפליין שרץ על push ועל PR, בסדר הזה:
  lint → tests → build → scan → push → helm lint → deploy → smoke test
- התראה על הצלחה או כישלון
- רכיב AI שרץ רק בכישלון: אוסף את הלוגים, שולח למודל שפה ומפרסם אבחון
- תיעוד: איך מריצים מקומית, איך ה-CI עובד, איפה האימג' מתפרסם ואיך מספקים סודות
- קישור לריצה שנכשלה, שבה רכיב ה-AI עבד

## 3. מוסכמות

### קומיטים

- מתחילים באות גדולה ובפועל בציווי
- בלי קידומות כמו `feat:` או `fix:`
- שורת כותרת קצרה, עד בערך 50 תווים, בלי נקודה בסוף
- קומיטים קטנים, ושינוי לוגי אחד בכל קומיט

דוגמאות:

```
Add health and readiness endpoints
Add multi-stage Dockerfile with non-root user
Configure Trivy scan to fail on critical findings
```

### אבטחת הפייפליין

- **כל GitHub Action חיצוני נעוץ ל-commit SHA מלא**, ולא לתגית כמו `@v4`.
  - הסיבה: במרץ 2026 תוקפים דחפו בכוח קוד זדוני ל-76 מתוך 77 התגיות של `aquasecurity/trivy-action`. כל workflow שהשתמש בתגית הריץ קוד שגונב סודות. SHA הוא בלתי ניתן לשינוי.
  - ליד כל SHA כותבים בהערה את הגרסה, כדי שיהיה קריא.
- **הרשאות מינימליות ל-`GITHUB_TOKEN`**, ומגדירים אותן בכל ג'וב בנפרד.

### תיעוד שוטף

- **יומן החלטות** בתיקייה `docs/decisions/`, בפורמט ADR קצר: הקשר, האפשרויות שנבחנו, ההחלטה והסיבה.
- **יומן תקלות** בקובץ `docs/troubleshooting.md`: התסמין, הסיבה והפתרון לכל בעיה שניתקל בה.
  - רשומה ראשונה: ב-WSL2, שירות עם `sessionAffinity: ClientIP` לא נגיש, וגם שום שירות שנוצר אחריו, כי חסר מודול בקרנל ש-kube-proxy צריך. ההגדרה הזו לא קשורה לזיהוי כתובת הלקוח, ולא משתמשים בה.

- **התכנון:**
  - סקריפט Python קטן, עם טסטים משלו
  - אוסף רק את הלוגים של הג'וב שנכשל, חותך אותם לקטע הרלוונטי ומסנן סודות

  - אם המודל לא זמין, מפרסם הודעת כישלון רגילה
  - הלוגים נחשבים קלט לא אמין: לא מריצים שום דבר שמגיע מהם, רק מפרסמים טקסט

### החלטה 10: צורת הרנר המקומי – ARC, ה-operator הרשמי של GitHub
- **עדכון 15.11:** במקור הוחלט על קונטיינר Docker זמני, ו-ARC נשאר לבדיקה בהמשך. מדידת המשאבים הראתה שיש לו מקום, ובהשוואה מחודשת הוא עדיף.
- **למה ARC:** זה הפתרון הרשמי של GitHub לרנרים על Kubernetes. ההזדהות מול GitHub היא GitHub App שמותקנת על הריפו הזה בלבד, עם הרשאת ניהול רנרים בלבד, וטוקנים של שעה. בקונטיינר Docker היינו צריכים התחברות של `gh` בשם רעות, עם גישה לכל הריפואים שלה. פוד הרנר רץ עם ServiceAccount משלו, כך שאין kubeconfig ואין טוקן לקלאסטר שצריך לייצר ידנית. ואין סקריפט לולאה לתחזק.
- **איך:** שני צ'ארטים רשמיים בגרסה 0.15.1, דרך `cluster/setup-arc.sh`. ה-controller ב-`arc-systems`, ו-scale set בשם `kind-staging` ב-`arc-runners`, מ-0 עד 2 רנרים. כל ג'וב מקבל פוד חדש שנמחק בסופו. בלי Docker-in-Docker ובלי privileged, כי הג'ובים המקומיים מריצים רק `helm` ו-`kubectl`. הרנר רץ כמשתמש שאינו root, עם מגבלת זיכרון של 1Gi, והאימג' נעוץ ל-digest. NetworkPolicy חוסם כל תעבורה נכנסת לפודי הרנר.
- **הסוד:** המפתח הפרטי של ה-GitHub App נשמר רק כ-Secret בשם `github-app` ב-`arc-runners`. הוא נוצר ידנית, לא בגיט, וקובץ ה-`.pem` נמחק מהמחשב.
- **נבדק בפועל, 15.11:** ה-listener התחבר ל-GitHub עם ה-App ונרשם. `kubectl auth can-i` בשם ה-ServiceAccount של הרנר: מותר ליצור Deployments, Secrets ו-HTTPRoutes ב-`staging` ולקרוא לוגים שם. אסור ב-`default`, אסור לקרוא Secrets ב-`arc-runners` או ב-`traefik`, כלומר הרנר לא יכול לקרוא את המפתח של ה-App, אסור למחוק פודים, ואסור ליצור namespaces או הרשאות ברמת הקלאסטר. הנוד צורך 1.24GiB, ונשארו כ-3.1GiB זמינים.
- **חלופה שנבחנה:** קונטיינר Docker זמני עם JIT config וסקריפט לולאה. פשוט יותר, אבל ההרשאה מול GitHub רחבה יותר, ויש יותר קוד וטוקנים שאנחנו מנהלים בעצמנו.

### החלטה 13: סריקת אבטחה – Trivy דרך ה-Action נעוץ ל-SHA
- **הכלי:** Trivy, הכלי הנפוץ ביותר לסריקת קונטיינרים ב-GitHub Actions, בקוד פתוח. החלופה המרכזית שנבחנה: Grype יחד עם Syft.
- **איך מריצים:** ה-Action הרשמי `aquasecurity/trivy-action`, נעוץ ל-commit SHA מלא, עם הגרסה בהערה. לפני שבוחרים SHA, מוודאים שהגרסה בטוחה ושהיא לא אחת מאלה שנפגעו במרץ 2026.
  - **חלופה שנבחנה:** להתקין את הבינארי בגרסה קבועה, עם בדיקת checksum. נדחתה כי היא דורשת יותר שורות לתחזק, ואין בה קאש מובנה.
- **איפה:** אחרי הבנייה, לפני ה-push ל-GHCR. אימג' פגיע לא מגיע לרג'יסטרי.
- **מתי נכשלים:** על ממצאים ברמת CRITICAL ו-HIGH, עם `ignore-unfixed`, כדי לא להיכשל על חולשות שעוד אין להן תיקון. חריגות מוצדקות נרשמות בקובץ `.trivyignore`, עם הסבר.
- **SBOM:** בפורמט CycloneDX, נשמר כ-artifact של הריצה.
- **הדוח:**
  - תמיד: טבלה בסיכום הריצה, ודוח SARIF שנשמר כ-artifact.
  - ללשונית Security: ההעלאה רצה רק כשהריפו ציבורי, עם התנאי `if: ${{ !github.event.repository.private }}`. בריפו פרטי של חשבון אישי, סריקת קוד דורשת GitHub Code Security, וההעלאה הייתה נכשלת.
  - הרשאה נדרשת להעלאה: `security-events: write`.

### החלטה 14: lint ופורמט – ruff לקוד Python, ו-hadolint ל-Dockerfile
- **למה ruff ולא flake8:** flake8 רק מדווח על בעיות. לידו צריך גם black לפורמט וגם isort לסידור ה-imports, כלומר שלושה כלים ושלוש גרסאות לנעוץ. ruff עושה את שלושתם, עם אותם קודים של חוקים כמו flake8, וכולל מובנים חוקים שב-flake8 דורשים תוספים, כמו bugbear וחוקי אבטחה בסגנון bandit. הוא יודע לתקן אוטומטית, וכל ההגדרות שלו יושבות ב-`pyproject.toml`.
- **מחיר ההחלטה:** ruff פרויקט צעיר יותר, ויש מאחוריו חברה מסחרית. המשימה נותנת את flake8 רק כדוגמה.
- **hadolint:** הכלי המקובל ללינט של Dockerfile. רץ דרך `hadolint/hadolint-action`, נעוץ ל-SHA מלא.
- **בפייפליין:** `ruff check`, `ruff format --check` ו-`hadolint`.

### החלטה 15: זיהוי ה-IP של הלקוח – uvicorn עם NetworkPolicy
- **האיום:** כל לקוח יכול לשלוח בעצמו כותרת `X-Forwarded-For` עם כתובת מזויפת. במערכת אמיתית אותה כתובת משמשת להגבלת קצב, לרשימות של כתובות מורשות, ללוגים ולחסימה לפי מדינה.
- **שכבה 1, Traefik:** בלי `trustedIPs` ובלי `insecure`, כי אין שום פרוקסי לפניו. מאמתים בניסוי מה הוא עושה עם כותרת שמגיעה מבחוץ.
- **שכבה 2, האפליקציה:** המנגנון המובנה של uvicorn, `--proxy-headers`, שקורא את הכותרת מימין ומדלג רק על כתובות מהימנות. את הרשימה מגדירים במשתנה `FORWARDED_ALLOW_IPS`, שמוגדר בקובץ `values.yaml` לטווח הכתובות של הפודים. אף פעם לא מגדירים אותו ל-`*`. הקוד מחזיר רק את `request.client.host`, ולא מנתח כותרות בעצמו.

### החלטה 21: ניתוב תעבורה – רק Gateway API, עם Traefik
- **מי עושה מה:** Traefik הוא התוכנה שמקבלת את התעבורה ומנתבת אותה, כלומר ה-controller. Ingress ו-Gateway API הם שני פורמטים לכתיבת כללי ניתוב, ו-Traefik יודע לקרוא את שניהם. צריך מימוש אחד ופורמט אחד.
- **למה Gateway API:** לפרויקטים חדשים ב-2026 זה הפורמט המומלץ. Ingress עדיין נתמך, אבל לא מפתחים בו יכולות חדשות. Gateway API מחלק אחריות לפי תפקידים: ה-Gateway, כלומר נקודת הכניסה, שייך להקמת הקלאסטר, וה-HTTPRoute שייך לצ'ארט של האפליקציה.
- **בצ'ארט:** רק `httpRoute`, מאחורי מתג. דולק ב-`values-staging.yaml`.
- **בהקמת הקלאסטר:** Traefik עם ה-provider של Gateway API, ה-CRDs הרשמיים של Gateway API, ומשאב Gateway בשם `web` ב-namespace `traefik`. בלי ה-CRDs של Traefik עצמו, שלפי מדידת המשאבים הם רוב העלות שלו.
- **מחיר ההחלטה:** המשימה כותבת "optional Ingress", ובודק עלול לחפש משאב Ingress. נסביר את הבחירה ב-README.
- **למה Traefik:** פרק 5. ingress-nginx פרש במרץ 2026. מדידת המשאבים הראתה ש-Traefik עולה כ-146MiB זמינים, ואחריו נשארים כ-3.3GiB.

### החלטה 23: הקלאסטר – NodePort ל-Traefik, רק ב-localhost
- **הקבצים:** `cluster/kind-config.yaml`, `cluster/traefik-values.yaml` ו-`cluster/setup.sh`, שמקים הכל בפקודה אחת ואפשר להריץ אותו שוב בבטחה.

- **למה NodePort:** התיעוד הרשמי של Kubernetes ממליץ להימנע מ-hostPort, כי הוא קושר פודים לנוד ולפורט מסוימים, וקורא ל-NodePort "the safer, Kubernetes-native way".
- **חלופות שנבחנו:** hostPort, שמופיע במדריכים ישנים של kind אבל התיעוד של Kubernetes ממליץ להימנע ממנו. cloud-provider-kind, שהתיעוד של kind ממליץ עליו היום והוא הכי דומה ל-production. לפי ה-README שלו, ב-WSL2 הוא "basically supported", דורש `sudo`, רץ כתהליך נפרד ברקע, חושף על פורט אקראי, ומוגדר כ-alpha. אפשר לנסות אותו בניסוי מוגבל בזמן ביום השני.
- **רק המחשב הזה:** `listenAddress: 127.0.0.1` במיפוי של kind, כך שמחשבים אחרים ברשת לא מגיעים ל-staging.
- **Gateway API:** ה-CRDs הרשמיים בגרסה v1.6.3, הגרסה ש-Traefik v3.7.18 נבנה מולה לפי ה-go.mod שלו. הסקריפט מוריד אותם ובודק checksum.
- **Traefik:** הצ'ארט בגרסה 42.4.0, עם `--skip-crds`, כי הוא מתקין 25 CRDs של Traefik ושל Traefik Hub שאנחנו לא צריכים. רק ה-provider של Gateway API דולק. הצ'ארט יוצר את ה-GatewayClass ואת ה-Gateway בשם `web`, שמקבל routes רק מה-namespace `staging`.
- **נבדק בפועל, 15.11:**
  - דרך ה-Gateway: `/` מחזיר `{"ip":"172.19.0.1"}`, כתובת של רשת Docker, כצפוי ב-kind. `/health`, `/ready` ו-`/docs` עובדים.
  - כותרת `X-Forwarded-For: 1.2.3.4` שנשלחה מבחוץ נזרקה.
  - פוד אחר ב-`staging` שפנה ישירות לאפליקציה עם כותרת מזויפת נחסם על ידי ה-NetworkPolicy. בלי ה-NetworkPolicy, אותו פוד קיבל `{"ip":"1.2.3.4"}`. כלומר האיום מהחלטה 15 אמיתי, ו-kindnet אוכף NetworkPolicy.
  - בפודים של האפליקציה אין volume של טוקן, כלומר `automountServiceAccountToken: false` עובד.
  - הנוד צורך כ-1GB, ונשארו כ-3.2GB זמינים ב-WSL.

### החלטה 24: מימוש רכיב ה-AI
- **עיקרון מנחה:** מתכננים כאילו הזרקת פרומפט תצליח, ומגבילים מה היא יכולה לעשות. לג'וב אין שום סוד של הריפו, אין לו הרשאת כתיבה לקוד, והוא לא מריץ שום דבר מהלוגים או מהתשובה. הדבר היחיד שהוא כותב הוא טקסט בתגובה אחת ובסיכום הריצה.
- **הרשאות:** `actions: read`, `models: read`, `pull-requests: write`.
- **כל הג'ובים:** הלוגים של ג'ובים שרצו על רנר ARC נשלחים ל-GitHub כמו כל לוג אחר, ולכן ה-AI מאבחן גם את `deploy` ואת `smoke-test`. הוא עצמו רץ על רנר של GitHub, כך שהוא זמין גם כשהרנר המקומי הוא הבעיה. ל-`deploy` ול-`smoke-test` יתווסף צעד שרץ רק בכישלון ומדפיס ללוג את מצב הקלאסטר: פודים, אירועים ולוגים. כשהרנר המקומי לא פועל, הג'וב מחכה בתור ולא נכשל, ולכן ה-AI לא רץ. זה יתועד ב-README.
- **הקוד:** החבילה `ci_diagnosis/`, עם טסטים ב-`tests/ci_diagnosis/`. התלויות שלה, `openai`, `httpx` ו-`pydantic`, בקבוצת התלויות `ci`, שלא נכנסת לאימג' של האפליקציה. קבוצת `dev` כוללת אותה, כך שה-lint והטסטים מכסים גם את החבילה.
- **הזרימה:** רשימת הג'ובים שנכשלו והצעדים שנכשלו בהם, דרך ה-API של GitHub. מכל לוג נשמרות השורות סביב השגיאות וסוף הלוג, עד 8,000 תווים בסך הכל. סינון סודות לפי תבניות, בנוסף להסתרה של GitHub. הלוגים נכנסים לפרומפט בתוך תוחמים, עם הוראה שהם מידע ולא הוראות. התשובה היא JSON באותו מבנה קבוע מהחלטה 5, ועוברת אימות של Pydantic.
- **ניקוי הפלט:** HTML מנוטרל, תמונות מוסרות כי טעינה שלהן יכולה להדליף מידע דרך ה-URL, מקישורים נשאר רק הטקסט, ו-`@mentions` מקבלים תו בלתי נראה כדי שאף אחד לא יתויג. שורות הראיות נכנסות לבלוק קוד, שהגדר שלו ארוך מכל רצף backticks בתוכו.
- **פרסום:** תמיד בסיכום הריצה. ב-PR, תגובה אחת עם סימון נסתר, שמתעדכנת בכל ריצה. בכישלון על `main` בלי PR, רק סיכום הריצה, יחד עם ההתראה במייל של GitHub.
- **כשל של המודל:** timeout, מגבלת קצב או תשובה לא תקינה מובילים להודעת כישלון רגילה עם רשימת הג'ובים. הג'וב תמיד מסתיים בהצלחה ומדווח על בעיות כ-warning, כדי לא להסתיר את הכישלון המקורי.
- **ספק המודל:** הספרייה הרשמית `openai`, מול כל API בפורמט של OpenAI. משתני הריפו `AI_API_BASE_URL` ו-`AI_MODEL`, עם ברירות מחדל ב-workflow: GitHub Models ו-`openai/gpt-4.1-mini`. הסוד `AI_API_KEY` נדרש רק לספק אחר. את המודל צריך לאמת מול הקטלוג בריצה הראשונה.
- **חלופות שנבחנו:** `httpx2` עם קוד HTTP משלנו, שהוא פחות תלויות אבל יותר קוד לתחזק. Issue בכישלון על `main`, שהוא גלוי יותר אבל דורש עוד הרשאת כתיבה.

## 7. בדיקת משאבים במחשב 🖥️

**מטרה:** לדעת בוודאות כמה זיכרון, מעבד ודיסק נשארים כש-Docker Desktop, kind ו-ARC רצים. ככה מחליטים על סמך מספרים ולא הנחות. **זה הצעד הראשון לפני הקמת הקלאסטר.**

**רקע:** המחשב של רעות עם Windows, 4 ליבות ובערך 22 ג'יגה זיכרון זמין. ל-WSL מוגבלים 6 ג'יגה ו-4 מעבדים, בקובץ `.wslconfig`. Docker Desktop רץ בתוך WSL, ולכן הוא חולק את אותה מגבלה.

**ההחלטה על הרנר לא משתנה:** ממשיכים עם קונטיינר Docker זמני, כמו בהחלטה 10. המדידה של ARC רק בודקת אם יש מקום לעבור אליו בהמשך.

### שלב 1: מדידת בסיס, Docker Desktop פועל ושום דבר אחר לא רץ

ב-PowerShell:

```powershell
Get-PSDrive C                       # מקום פנוי בדיסק C
Get-Content $env:USERPROFILE\.wslconfig   # המגבלות שהוגדרו ל-WSL
wsl --list --verbose                # אילו הפצות WSL רצות
```

בתוך WSL:

```bash
free -h            # זיכרון: כמה מוקצה, כמה בשימוש, כמה זמין

df -h /            # מקום בדיסק בתוך WSL
docker system df   # כמה מקום תופסים אימג'ים, קונטיינרים ו-volumes
docker stats --no-stream
```

### שלב 2: אחרי הקמת kind

## 8. מידע רקע מהמחקר

- **רנר מקומי בריפו ציבורי:** GitHub ממליצה לא לחבר רנר מקומי לריפו ציבורי. ההגנה המובנית דורשת אישור רק ל-PR הראשון של תורם חדש.
- **עלות רנר מקומי:** GitHub הודיעה בדצמבר 2025 על תשלום לפי דקה, ודחתה את זה. נכון לעכשיו השימוש חינמי.
- **צריכת זיכרון של kind:** נוד אחד צורך במנוחה בערך 300 עד 600 מגה. ב-WSL של רעות הוקצו 6 ג'יגה.
- **זיהוי ה-IP:** מאחורי פרוקסי או Ingress, הכתובת מגיעה בכותרת X-Forwarded-For. ב-Service, ההגדרה `externalTrafficPolicy: Local` שומרת על כתובת המקור.
- **מה רואים מקומית:** ב-kind לא רואים כתובת ציבורית, אלא כתובת של רשת Docker, משהו כמו `172.18.0.1`. זה צפוי, ונתעד את זה ב-README.
- **ניסוי מוצע:** נקודת קצה זמנית לדיבאג, שמחזירה את כתובת החיבור ואת כל הכותרות. מריצים דרך port-forward, דרך NodePort ודרך ה-Ingress, ומתעדים מה מגיע בכל אחת. אחר כך מוחקים אותה.
